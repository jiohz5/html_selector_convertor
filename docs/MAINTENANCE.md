# 입력 형식과 디자인 유지보수

원본 사이트의 운영 종료와 우리 도구의 지원 종료는 별도로 판단한다. 원본 데모가 없어져도 보관한 디자인 레시피·키트·엔진이 정상 동작하면 해당 디자인을 계속 제공한다. 링크 오류나 iframe 차단만으로 디자인 ID와 레시피를 삭제하지 않는다.

이 문서는 HTML 입력 구조와 이후 유지보수 원칙을 정리한다. 원본 렌더링·분석과 두 출력 모드는 구현했으며 폴더판·단일판 통합 회귀를 검증했다. 디자인 상태 필드, 레시피 revision별 제공, 출력 버전 메타데이터, 외부 자산 보존 모드는 후속 제안이며 아직 구현되지 않았다.

## 입력 형식 추가

입력 판별은 전용 reader 목록에서 관리한다. 각 reader는 ID, 확장자, 화면 안내, 텍스트 지원 정보, 읽기 함수를 갖는다. 같은 목록에서 파일 선택창의 accept, 지원 형식 안내, 원문 텍스트의 수동 형식 선택 목록을 생성한다. 알 수 없는 확장자를 CSV로 읽지 않는다.

파서는 표 `{columns, rows}` 또는 기존 spec을 반환하고, 열 역할 판별·집계·HTML 생성은 공통 경로를 사용한다. 파일 형식별로 계산 엔진과 렌더러를 다시 만들지 않는다. 여러 표나 시트가 있으면 원본 선택 정보를 함께 반환한다.

파일과 붙여 넣은 원문 텍스트는 같은 reader·profile·spec·render 경로를 사용한다. 텍스트 형식은 자동 감지 또는 CSV(.csv)·TSV(.tsv)·TXT(.txt)·JSON(.json)·HTML(.html)·HTM(.htm)으로 선택한다. 자동 감지는 `{`·`[` 시작을 JSON, `<` 시작을 HTML, 일관된 구분표를 CSV·TSV로 판별한다. 애매한 본문은 형식 선택을 요청하며 JSON·HTML 읽기 실패를 CSV로 우회하지 않는다.

붙여넣기 실패 시 수정할 수 있도록 입력 본문은 유지하고 이전 결과는 제거한다. 엑셀 바이너리는 텍스트 형식 목록에 넣지 않으며, 복사한 셀의 TSV·CSV는 기존 표 reader로 처리한다. 기본 HTML 읽기에서 스크립트를 비활성으로 처리하며 파일과 원문 텍스트에 같은 경로를 적용한다. 사내·외부 모델 연결은 추가하지 않는다.

형식을 추가할 때 다음을 한 변경으로 묶는다.

1. 지원 범위를 정의한다. 표·본문·내장 데이터·원본 모양 중 무엇을 읽는지 명시한다.
2. reader·확장자·텍스트 지원 정보를 등록하고 동일 표/spec 모델로 변환한다. 지원 형식 목록을 화면에 별도로 중복 작성하지 않는다.
3. 정상·빈·손상·범위 밖 입력 fixture와 독립적인 기대값을 추가한다.
4. 파일 선택과 끌어다 놓기에서 같은 판별을 적용하고, 텍스트 지원 형식은 자동 감지와 수동 선택도 함께 검사한다.
5. 여러 표 선택, 오류 후 이전 결과 제거, 연속 입력을 검사한다. 붙여넣기 본문 유지, 모호한 자동 감지, 손상 JSON·HTML의 CSV 우회 금지도 확인한다.
6. 브라우저와 Python의 지원 범위 차이를 README에 적는다.
7. 단일 파일 배포본을 다시 만들고 같은 fixture를 검사한다.

HTML은 정적 표, 인라인 `script[type="application/json"]`의 레코드 배열, 우리 출력의 `hc-spec` 재불러오기를 지원한다. 일반 HTML의 CSS·스크립트·이미지·상호작용을 복제하는 기능과 구분한다. 병합 셀·중첩 표·여러 줄 머리글은 지원 범위를 넓힐 때 각각 fixture를 추가한다.

기본 비실행 읽기에서 `hc-spec` 표식이 있으면 먼저 검증하고, 유효 spec을 복원하거나 손상 오류를 반환한다. 손상 spec을 다른 표·JSON으로 대체하지 않는다. spec이 없는 HTML에서는 정적 표와 내장 JSON 후보를 같은 목록으로 반환한다. 첫 유효 정적 표를 기본 선택하며, 없으면 첫 유효 JSON을 사용한다. 후보 오류는 선택 목록에 사유를 남기고 JSON 후보에는 script ID·경로·행 수를 표시한다.

내장 JSON은 객체 경로를 탐색하되 배열에서 멈춘다. null이 아닌 객체만으로 구성된 레코드 배열을 표로 변환하고, 전체 행의 키 합집합으로 열을 만든다. 레코드 셀의 객체·배열은 JSON 문자열로 보존하며 내부 배열을 새 데이터 후보로 다시 탐색하지 않는다. 속성의 스칼라 배열은 제외하고 빈·혼합·null 행이 있는 레코드 후보는 오류로 표시한다. JSON-LD, 일반 JavaScript, `src`가 있는 script는 대상에서 제외하고 외부 자산을 실행하거나 불러오지 않는다. HTML 내장 JSON의 객체 경로 탐색을 일반 JSON 파일의 지원 확대와 혼동하지 않는다.

기본 정적 표·내장 JSON 읽기는 원본 페이지의 계산·집계·입체 SVG·조작 기능을 재현하거나 원본 JavaScript를 실행하지 않는다. 유지보수 fixture는 작은 예시 데이터로 만든다. 빈 정적 표와 유효 JSON의 조합, 표 우선 선택, 여러 script·경로 선택, 후반 행의 추가 열, 셀 객체·배열 보존, 오류 후보와 외부 script 제외를 각각 검사한다.

## HTML 원본 렌더링과 두 모드

기본 비실행 입력 경로를 유지하고, HTML 입력 패널에서 사용자가 **원본 렌더링·분석**을 선택할 때만 전용 격리 renderer를 사용한다. 기존 생성 결과의 미리보기 frame은 원본 실행에 재사용하지 않는다. 원본 미리보기와 제목·머리글·본문, 표·SVG·canvas 수를 제공하며 원문 HTML과 렌더 DOM을 구분해 보관한다.

| 모드 | 출력과 지원 범위 |
|---|---|
| 원본 유지 | 업로드한 파일은 원본 File Blob으로 다운로드하여 BOM·문자 인코딩 바이트를 보존한다. 붙여 넣은 원문은 UTF-8 BOM을 붙여 저장하여 legacy charset 선언보다 입력한 Unicode 텍스트의 인코딩을 우선한다. 원본 배치·코드·동작을 보존하며 현재 디자인 토큰으로 다시 만들지 않는다. |
| 다른 느낌(새 디자인) | 유효한 렌더 DOM 표를 내장 spec·JSON보다 먼저 읽어 기존 parser·profile·spec·renderer 경로로 재구성한다. 없으면 유효 spec → 내장 JSON → 제목·본문 기반 spec 순서로 사용한다. |

선택적으로 실행한 뒤 새 디자인으로 적용하는 경로의 우선순위와 기본 비실행 읽기의 `hc-spec` 우선 복원 계약은 구분한다. 기본 읽기와 새 디자인 적용은 손상 `hc-spec`에 오류를 표시하며 다른 표·JSON·본문으로 대체하지 않는다. 렌더 DOM 표 우선 선택은 유효 spec이 있거나 spec 표식이 없는 HTML에 적용한다. 원본 유지의 원문 저장은 별도 경로이며 분석 결과를 확인한 뒤 그대로 보존할 수 있다. 표 태그가 있어도 읽을 데이터 표가 없고 본문이 있으면 수치 집계 없이 본문을 사용하며, parser가 표를 읽지 못한 사유를 분석 안내에 표시한다.

기본 collector는 `DOMContentLoaded` 후 초기 2초를 기다리고 본문·표가 800ms 안정됐는지 확인하며, 전체 제한 시간은 8초다. 이 기준은 초기 화면을 읽기 위한 휴리스틱이며 늦게 추가되는 비동기 데이터의 완결성을 보장하지 않는다. 유지보수 회귀에 초기 지연 표 생성과 제한 시간·부분 결과를 포함하고 이 한계를 화면에 안내한다.

새 디자인 모드는 원본의 임의 SVG·canvas·조작 기능을 같은 모양과 동작으로 자동 변환하지 않는다. 원본 유지에서도 온라인 자산·API·storage 의존성은 원문에 남으므로 해당 환경이 없을 때 동작이 제한될 수 있다. 원본의 외부 통신을 제한한 분석 미리보기와 원문 파일을 직접 여는 환경의 동작은 달라질 수 있다. 외부 자산까지 내장하는 장기 보존 모드는 별도 과제다.

renderer는 바깥 frame과 원본을 담는 안쪽 frame 모두에 `sandbox="allow-scripts"`를 사용하고 `allow-same-origin`을 허용하지 않는다. 바깥 frame의 CSP에는 `frame-src 'none'`을 포함하며 원본 외부 통신도 CSP로 제한한다. Chromium 기반 Edge의 `file://`와 HTTP 환경에서 수행한 독립 probe는 이 구성의 원본 navigation·외부 통신·부모 DOM 접근 차단을 확인했다. 이 구성을 실제 모듈에 반영했으며 폴더판·단일판의 합성 회귀 19개 그룹을 각각 통과했다. 다른 브라우저·실행 환경의 같은 동작을 보장하지 않는다.

원본 유지 모드의 새 창 열기는 부모 권한으로 원본을 실행하지 않도록 비활성으로 두고, HTML 다운로드 후 사용하는 흐름으로 제공한다. 무한 루프의 강제 중단을 보장하지 않는다. 원문 교체·모드 전환·취소·오류 이후 이전 분석이나 결과가 다시 적용되지 않는지 검사한다. 이 흐름은 모델 API 연계를 추가하지 않으며 기존 문장 다듬기는 숨김 상태를 유지한다. 첨부 원문·파일명·실제 수치를 공개 문서나 fixture에 넣지 않는다.

## 원본 사이트 없이 계속 제공하기

현재 `render.py`와 `HC.build`는 원본 데모 주소를 읽지 않는다. `html-convertor/references/designs.json`, 로컬 키트, 공통 CSS, `engine.js`, spec을 사용한다. 결과 HTML에는 spec·엔진·키트·디자인 토큰이 포함된다.

차트 JS·일부 디자인 CSS·웹폰트는 외부 CDN을 사용한다. 따라서 저장된 HTML은 데이터 명세와 자체 렌더링 코드를 보존하지만, 당시의 외부 자산까지 전부 보존한 것은 아니다. 차트가 로드되지 않으면 값 표로 대체되는 동작은 있으나 발표 라이브러리·CSS·폰트까지 같은 수준의 대체를 보장하지 않는다.

원본 사이트가 종료되면 기존 레시피를 유지하고 데모 접속 안내를 갱신한다. 현재는 목록 설명에 기록하고, 상태 필드를 도입한 뒤에는 데모 접속 상태를 별도로 갱신한다. 생성 결과의 외부 자산이 사라지면 검증한 버전의 자산 보관 또는 의존성 교체를 별도 변경으로 수행한다. 원본 종료 자체는 우리 지원을 끊는 이유로 사용하지 않는다.

저장 HTML을 그대로 열기는 저장 당시 출력 재사용이다. 내장 spec을 다시 읽기는 저장된 내용을 현재 레시피와 선택한 디자인으로 다시 만드는 기능이다. 레시피가 바뀌면 후자의 모양은 달라질 수 있다.

## 디자인 상태 관리 제안

다음 필드는 후속 카탈로그 개선에서 도입한다. 현재 데이터에 이미 구현된 필드는 아니다.

| 필드 | 의미 |
|---|---|
| upstreamStatus | 원본 프로젝트 상태: active, retired, unknown |
| previewStatus | 데모 접근 상태: available, unavailable, blocked, unknown |
| renderStatus | 우리 지원 상태: maintained, frozen, disabled |
| recipeRevision | 레시피 변경 번호 |
| lastVerifiedAt | 실제 생성·화면을 마지막으로 검증한 날짜 |
| statusReason | 상태 판단의 근거 |

frozen은 검증한 기존 레시피를 계속 제공하되 원본의 새 버전을 따라가지 않는 상태다. 원본 지원이 끝난 디자인도 frozen 상태로 유지할 수 있다. disabled는 우리 쪽 렌더링이 실제로 실패하고 해결되지 않을 때 사유와 함께 설정한다.

디자인 ID는 영구 식별자로 유지한다. 기존 ID를 다른 디자인에 재사용하지 않는다. 목록에서 숨길 때도 과거 내보내기 파일을 해석하는 카탈로그 정보와 레시피를 보관한다.

## 디자인과 키트 추가

1. `assets/templates.js`에 고유 ID와 목록 정보를 추가한다.
2. `sync_catalog.py`로 `catalog.json`을 동기화한다.
3. 같은 ID의 레시피를 `designs.json`에 추가하고 키트·차트·테마·외부 자산을 확인한다.
4. 새로운 레이아웃 유형이면 키트의 spec 소비 규칙과 Python·브라우저 렌더러를 함께 갱신한다.
5. 밝은 화면·다크 화면·모바일·차트·표를 검증한다.
6. 렌더러 비교와 독립 fixture 회귀 검사를 실행한다.
7. 번들과 단일 파일을 재생성한다.

현재 레시피 변경과 변경 이유는 Git 이력에 남긴다. 후속 revision 관리에서는 변경 번호를 올리고 이전 레시피를 보관한다. 큰 변경 전에 기존 레시피·출력을 보관하고, 외부 자산 보존도 필요하면 함께 준비한다. 검증된 예전 revision을 선택해 계속 생성하는 기능은 별도 구현 과제다.

## 동기화 개선 과제

templates는 목록 원본, catalog는 스킬용 사본, designs는 렌더링 원본이다. ID 관계와 공유 필드 일치성을 검사해야 한다. 현재 `build_bundle.py --check`는 catalog를 검사하지 않는다.

`sync_catalog.py`는 복사할 필드를 제한하므로 새로운 상태 필드를 추가할 때 복사 규칙에도 반영한다. 또한 이전 catalog의 sourcePath보다 현재 저장소의 `assets/templates.js`를 우선하도록 개선한다. 개선 전에는 `python html-convertor/scripts/sync_catalog.py assets/templates.js`로 현재 저장소 파일을 명시한다. 다른 checkout의 파일을 우연히 동기화하지 않아야 한다.

`resolve_design.py`는 catalog에 없는 ID를 해석하지 못한다. 원본 종료된 항목을 templates·catalog에서 단순 삭제하면 레시피가 남아 있어도 과거 내보내기의 지원이 끊긴다. 현재는 기존 항목을 유지한다. 후속 상태 관리와 보존 목록에서도 기존 ID를 계속 해석하도록 한다.

## 버전과 장기 보존 제안

후속 출력 메타데이터에는 spec 스키마 버전, 렌더러 버전, 번들 해시, 디자인 ID·recipeRevision, 실제 적용 옵션을 남긴다. 옵션에는 kit, chartLib, theme, layout, kpiStyle, 사용자 tokens·CSS를 포함한다. 현재 hc-config는 mode, chartLib, theme, design, kit만 저장하며 버전·revision·번들 해시는 결과 설정에 남기지 않는다.

버전 필드가 없는 기존 spec도 읽도록 호환성을 유지한다. 호환성에 영향을 주는 변경은 이전 형식 fixture와 변환 규칙을 함께 추가한다. 지원하지 않는 미래 버전을 조용히 다른 입력으로 해석하지 않는다.

보존 모드는 차트·CSS·폰트를 함께 내장하거나 동봉하고 파일별 버전·해시를 기록하는 별도 작업이다. 자산 포함 범위와 재배포 조건을 확인해 패키지를 만든다. 구현·검증이 끝나기 전에는 완전 오프라인 재현을 지원한다고 표시하지 않는다.

## 유지보수 검증

아래 표는 유지보수에 필요한 검증 기준이다. 기존 검사는 렌더러 일치와 현재 spec의 정적 구조를 확인하며, 디자인 수명주기·외부 자산 보존 검사는 해당 기능과 함께 추가해야 한다.

| 검증 | 확인하는 내용 |
|---|---|
| 입력 정확성 | 독립 원자료에서 기대 열·행·값·집계가 나오는가 |
| 렌더러 일치 | 같은 spec과 옵션으로 Python과 브라우저가 같은 결과를 만드는가 |
| 저장 결과 재사용 | 예전 HTML의 spec을 읽어 값과 문장을 보존하는가 |
| 의존성 장애 | 데모가 없어도 생성되고, CDN 차단 시 명시한 대체가 동작하는가 |
| 지원 상태 | 원본 retired 항목도 선택·내보내기·해석·생성이 이어지는가 |

같은 오류를 가진 두 렌더러도 일치 검사에는 통과할 수 있다. 입력 기대값과 저장 결과 fixture를 따로 검사한다. 기존 `run_regress.py --compare`는 차이·비교 대상 누락만으로 실패하지 않으므로, 이를 배포 기준에 사용할 때 실패 종료 처리도 보강한다.
